# Dynamic model routing through Codex App Server

## Outcome

The project-local skill and lifecycle hooks remain advisory and protective.
They classify prompts, add sanitized developer context, and gate unsafe tool
execution, but they cannot change the model of an already-started stock TUI
turn.

The opt-in App Server manager is the separate switching layer. It rewrites the
installed `turn/start` fields before the real App Server receives the request:

```text
original Codex TUI
  codex --remote ws://127.0.0.1:<proxy>
        |
        v
localhost Smart Router WebSocket proxy
        |
        v
codex app-server --listen ws://127.0.0.1:<backend>
```

This is an independent local prototype. It is not an official OpenAI product
or endorsement.

## Installed protocol contract

Implementation was verified against schemas generated by installed
`codex-cli 0.144.6`:

```bash
codex app-server generate-json-schema --out /tmp/codex-app-server-schema
codex app-server generate-ts --out /tmp/codex-app-server-ts
codex app-server generate-json-schema --experimental \
  --out /tmp/codex-app-server-schema-experimental
codex app-server generate-ts --experimental \
  --out /tmp/codex-app-server-ts-experimental
```

The audit index is in
`smart_codex/app_server_router/schemas/INSTALLED_PROTOCOL_0_144_6.md`.
Routed mode fails closed when the installed version differs; regenerate and
review the schema before enabling it after a Codex upgrade.

The installed schema confirms per-turn `model`, `effort`, `sandboxPolicy`, and
`approvalPolicy` overrides. `turn/steer` has no such fields and is never
modified. WebSocket App Server transport is currently experimental and
unsupported, so this phase is opt-in and localhost-only.

## Startup discovery

Before accepting a TUI connection, the manager opens a separate initialized
metadata connection to the backend and calls:

1. paginated `model/list` with hidden entries included; and
2. `configRequirements/read`.

The resulting process-local registry stores only retrieval time, Codex version,
model identifiers/display metadata, visibility, upgrade target, supported
reasoning efforts, default effort, input modalities, and default status. It
stores no prompts, auth data, tokens, cookies, or credentials.

A returned model is treated as available to this App Server session. Hidden
models are never routed. Models with `upgrade` or `upgradeInfo.model` are marked
deprecated; a compatible visible live upgrade target wins. The live response
always wins over the separate Luna/Terra/Sol research snapshot.

## Selection policy

Policy is declarative in `rules/app_server_model_policy.json`. The central
Router Core supplies category, complexity, risk, context, action danger,
sandbox, and approval decisions. Model strength is then selected independently
from action authority:

| Capability class | Typical work | Typical effort |
|---|---|---|
| Luna | email/text, summaries, documentation, harmless small tasks | low/medium |
| Terra | normal coding, tests, repo maintenance, moderate research and grants | medium/high |
| Sol | architecture, complex refactors/debugging, security/math, deep research | high/xhigh/max |
| Spark | live text-only small targeted rapid edits when context and risk fit | low |

Known model IDs are preferences, not a permanent catalog. Class patterns also
use sanitized live display/description metadata, then fall back across declared
capability classes and finally to the best compatible visible live model.

Spark requires a concrete rapid-edit signal, text input, small/medium context,
low/medium complexity and risk, and no destructive/secret/deployment/database
action. If Spark is absent or unsuitable, selection falls back to Luna, Terra,
then Sol.

`ultra` is selected only when the live model advertises it, a complex supported
category contains a concrete delegation signal, and the prompt is not a
deterministic/reproducibility eval. The reason is recorded as sanitized policy
evidence. All other unsupported efforts resolve to the nearest advertised live
effort.

## Safety mapping

The selected model never determines authority. A Gmail send can use Luna and
still retain read-only/on-request policy. A default-branch deletion can use
Terra and still remain critical, read-only, and on-request under the Router
Core and hooks. Selecting Sol cannot loosen any policy.

Routed mode locally permits only:

- sandbox modes `read-only` and `workspace-write`;
- approval policies `on-request` and the stricter `untrusted` fallback; and
- the human `user` approval reviewer; and
- turn policies with network access disabled.

Managed requirements can tighten a route. If no safe intersection exists, the
proxy returns a sanitized routing error and does not forward the turn. Existing
`readOnly` or `untrusted` turn settings are preserved when they are stricter.
`danger-full-access`, `never`, and automatic approval review are never emitted.

## Transparent protocol behavior

For every frontend connection the proxy creates one backend connection.
Non-`turn/start` JSON text frames are forwarded unchanged. Backend responses,
streamed notifications, errors, approval requests, user-input requests, MCP
elicitations, auth-token refresh exchanges, attestation exchanges, and client
responses retain their IDs, payloads, and order. The proxy never answers any
server request on the user's behalf.

For `turn/start`, all input items and unrelated fields remain intact. The five
stable installed model/effort/safety fields are added or replaced. The stock remote TUI
also supplies the installed experimental `collaborationMode` field, whose
nested settings take precedence over top-level model and effort. When this
object is already present, the router aligns only `settings.model` and
`settings.reasoning_effort`; it preserves the mode and developer instructions.
The raw combined user text exists in memory only long enough to call Router
Core and capability mapping; it is then forwarded inside the original App
Server request as normal.

## Sanitized switching evidence

The event stream records only a prompt SHA-256, route category/class, original
session model when available, selected/forwarded model, effort, sandbox,
approval and status. String request/thread IDs are hashed. Raw prompt text is
never logged.

Evidence stages are:

- `thread / initialized`: original App Server thread model and effort;
- `route / forwarded`: selected values placed on the outgoing `turn/start`;
- `route / accepted`: the backend accepted that exact request ID;
- `active_settings / observed`: subsequent `thread/settings/updated` model and
  effort, when emitted; and
- `model_rerouted / observed`: a backend-reported reroute, when emitted.

Forwarded values prove proxy rewriting. Actual active-model proof should also
use `active_settings` or backend reroute evidence; do not infer it from an
advisory hook recommendation.

## Controlled original-TUI acceptance

On 2026-07-19, the installed `codex-cli 0.144.5` TUI was connected through the
localhost manager. Three harmless, completed turns produced this sanitized
evidence in one thread:

| Stage/category | Original setting | Forwarded setting | App Server active setting | TUI footer |
|---|---|---|---|---|
| thread initialization | Sol / max | — | Sol / max | Sol / max |
| email | Sol / max | Luna / low | Luna / low | Luna / low |
| testing analysis | Luna / low | Terra / medium | Terra / medium | Terra / medium |
| architecture analysis | Terra / medium | Sol / xhigh | Sol / xhigh | Sol / xhigh |

The event file contained hashes and the fields described above, not the prompt
text. This proves real rotation for that installed-version acceptance run; it
does not remove the experimental transport warning or the version pin.

Phase 5.3 repeated acceptance from Sol / `max` with exactly 12 harmless turns.
All 12 outgoing settings were backend-accepted and matched a subsequent
`active_settings` event, including observed Luna, Terra, Sol, and Spark
rotation. The complete task-class table, two post-soak calibration corrections,
and retained protective-skill stops are documented in
[`MODEL_CALIBRATION_EVAL.md`](MODEL_CALIBRATION_EVAL.md#original-tui-12-turn-soak).

## Known limitations

- WebSocket transport is experimental and unsupported.
- Registry metadata is refreshed at manager startup, not during a process.
- Image-plus-text turns are supported through modality filtering; image-only
  turns fail safely and can be retried in ordinary Codex.
- Turns carrying an experimental named `permissions` profile fail safely,
  because that field cannot coexist with the routed `sandboxPolicy` override.
- `turn/steer` cannot rotate models because the installed schema has no
  overrides.
- The manager supports local plain WebSockets only; it does not implement
  remote TLS or bearer-token ownership.
- Provider-side rerouting can still occur and is reported when App Server emits
  `model/rerouted`.
